# Statistics accounting proposal (#9)

Status: exploratory, not approved. `statistics/overview` and `statistics/nodes` retain the historical design canvas. The separate `statistics/accounting-*` states explore a prospective accounting projection using synthetic records. Browser specimens are not native validation or evidence that the engine currently provides these values.

## Recommended semantics

The default cohort contains settled roots with qualified finish times, grouped once by their local start day within the selected 7, 30, or 90 calendar days. The fixture clock is 2026-10-27 12:00 in Asia/Jakarta (UTC+07:00). A run crossing midnight belongs to its start day. Active work is separate and shows provisional usage and elapsed time to that fixed clock; it is excluded from settled averages. An alternative is to include active work in the default view, but that mixes changing and settled values. An end-day cohort would favor recently finished long runs instead; the start-day recommendation makes launch cohorts stable.

Repository, workflow, kind, status and time select root runs or standalone tasks. Node, harness and requested/observed model narrow execution contributions within those roots. A root without matching execution evidence is excluded. Ambiguous-only matches retain the root and visible unavailable coverage, but contribute no additive usage or execution duration. Run chart time is the whole root wall clock, even after contribution filters; standalone task time is the sum of all its qualified execution intervals, excluding idle gaps. Both duration policies preserve the whole matching root when contribution filters narrow usage and execution rankings. Nested run wall time is not added again. Execution rankings sum distinct intervals and can exceed wall clock when work overlaps. A model filter therefore does not turn run wall time into model execution time.

An execution is an accounted attempt or explicitly identified continuation, not a message or repeated cumulative snapshot. Retries are separate; historical resume segments without evidence remain unavailable. The root owns descendant contributions once; orchestrator control work is a distinct contribution. Native-child transport copies are evidence, not additive without proof of disjoint ownership. Turn attribution is unavailable when only segment totals exist; totals are never divided across messages. Requested and observed models are separate; unknown observed identity stays unknown.

Usage is a known token subtotal, not a complete total unless every expected contribution has qualified usage and ownership. Only explicitly normalized, disjoint totals with category-inclusion provenance enter the scalar. The fixture includes one backend where cache categories are disjoint from input and another where cache read is included in input. Category subtotals may overlap and must not be added blindly. Missing is distinct from reported zero; category availability, qualified and unavailable execution counts, and complete/partial/unavailable root counts remain visible. Ambiguous ownership is excluded. A stricter alternative would hide partial root subtotals entirely; it avoids comparisons of incomplete work but discards useful reported evidence. The recommendation labels known subtotals and their exclusions explicitly.

## Fixture and states

The immutable ledger in `scripts/statistics-accounting.js` includes root and standalone work, nested and control contributions, retry and resume, a fallback observed model, unknown repository/model, partial categories, reported zero, active work, a cross-midnight run, ambiguous native-child evidence, and a root with a missing qualified completion witness. Synthetic segment timestamps establish idle gaps and overlapping execution intervals; status and completion qualification belong to each segment independently of its root.

The missing-witness root and active roots are excluded from settled accounting, with counts scoped by the same selected filters and time range.

A second identical snapshot of e2 carries the same contributionId and is normalized once before aggregation. The model exposes raw and unique matching evidence counts and the number of repeated copies removed. Conflicting copies fail closed as ambiguous evidence. This is a prospective stable-identity projection rule; it does not reconstruct backend cumulative streams or establish their production normalization semantics.

Daily values, contribution groups, totals and bounded lists derive from those records. Filters reset pagination; navigation preserves filter context and returning from detail restores the invoking Inspect control. Active deep links initialize the live cohort; list, execution-detail and Back transitions retain that cohort. A separate Active work control makes the live cohort accessible; the settled Status menu offers only settled statuses. Retry preserves the current local options. Task messages and segment totals appear as separate lists. Nested boundaries appear only on their actual parent, using explicit nested-run ledger records. Entirely unavailable scalar or category evidence renders Unavailable; a qualified reported zero remains zero.

The overview ranks workflow groups by total matching run wall time or known token subtotal, showing run count, total and mean wall time with the qualified-run denominator, usage coverage, and harness/observed-model attribution. Each workflow expands to at most eight contributing runs and links to its workflow-scoped two-row paged run list. A second settled Implementation run makes the grouping and totals inspectable. At most eight workflow groups and eight standalone task rows appear in the overview; all values derive from the same ledger as the full lists.

Time/Usage changes both ranking order and the daily chart. Each root row discloses duration and coverage policy; execution groups show independent segment status, mean duration with interval count, and share with an explicit denominator.

Daily stacked bars include every selected calendar day at a uniform interval, including zero elapsed days without reported usage. Qualified zero-token days have a distinct baseline dot. The 30/90-day views use thin bars and sparse date labels; the legend reports workflow, standalone, and combined totals. All bars use one common scale; an accessible daily data table provides values and units.

Root averages keep workflow wall time and standalone execution time separate. Context launch specimens illustrate placement only and do not change existing workflow screens.

The no-matches specimen selects the real team-b repository plus Implementation workflow combination in its visible toolbar. Standalone node and workflow filters use Standalone task and No workflow rather than Unknown; missing repository/model identity remains Unknown. The elapsed tiles explicitly disclose whole-root, nonadditive contribution-filter semantics in both cohorts. Incomplete disclosures derive from the scoped excluded root records.

Loading, read failure/retry, no retained history, no filter matches, partial evidence, active work, paged run/task lists, execution detail, task messages, and contextual launches are exploratory design states. They do not imply an existing native implementation. Browser controls, typography and material effects approximate macOS; actual native pixels, accessibility and live behavior remain unverified.

## Engine prerequisite

Product integration requires an engine-owned, bounded public accounting projection with stable contribution identities, ownership and scope, normalized categories and inclusion provenance, qualified timestamps, requested/effective/observed model provenance, retained-history and coverage witnesses, consistent pagination and invalidation. Mac must consume that public interface rather than read private task records or replay historical streams. Current listing headers omit accounting; backend snapshots have differing accumulation semantics, and native-child usage may copy transport evidence. The current Mac agent usage repository ranks acknowledged submissions rather than measured execution accounting. These fixture values are prospective, not claims about current engine support. No contract change is proposed as already implemented.

## Review and validation boundary

The proposal has no runtime connection, retained-history query, dynamic refresh, real calendar-zone conversion, or native accessibility verification. The fixture uses fixed UTC+07 timestamps and clock. Context cards illustrate entry placement, not full workflow/run/repository screens. Browser interaction and appearance validation must be recorded separately from syntax and catalog tests. Production integration, accounting policy approval, and native implementation remain pending.
