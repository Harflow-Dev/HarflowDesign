## Exploratory ticket proposals

The registry (`scripts/registry.js`) is the single source for proposal marking. A state listed in a family's `proposals` map, or any state of a family with a `proposal`, is exploratory: the catalog caption reads "Exploratory · ticket #N · Not approved", the state picker and navigation search carry "Exploratory", and the stage repeats the label above the specimen. A `scope: 'element'` entry marks a source-derived state that contains an exploratory element; its caption reads "Source-derived · contains exploratory element (#N) · Not approved" and it has no stage label. None of these designs is approved. Ticket references are `#N` for HarflowMac, `HarflowMCP#N` for the engine, and `HarflowWeb#N` for the web app. The catalog groups families by platform (macOS and Harflow web) and sets the eyebrow to HARFLOW / WEB for the web family.

Not designed: Statistics empty state and missing history, loading, error, contextual entry points from workflow, run and repository views, filter menu contents and behaviour, disclosure of running or incomplete runs excluded from averages, nested-workflow and orchestrator/control attribution on the node breakdown, retries and resumed executions, the full run list behind "Show all N runs", the full task list, an unknown or unreported model under a harness, and what counts as one execution for a task (#9); Council no-consensus, cancellation, empty (no candidate yet), loading, and unsupported-engine states, independent opening positions, pending and unresolved questions, missing evidence, per-member status in the roster beyond departure, transcript paging and reading position during streaming (#17 run), readiness cancelled, failed, and pre-run disclosure and working-directory selection (HarflowMCP#18), concurrent-edit handling for rename (#4), the referenced-workflow delete policy (#8), sidebar search and filter interaction with starred order beyond the stable-order rule (#7), and persistence by workflow identity (#7); workflow setup and teardown run states (setup timed out, teardown running beyond the mock transition, teardown failed, and cancel during setup), defining workflow inputs, entering them at launch, and mapping child workflow inputs, empty-command and timeout validation, the Run sheet when a workflow has only setup or only teardown, child workflow commands in the Run sheet, and leftover workspace cleanup (#21, HarflowMCP#41); the web app's Login (HarflowWeb#3), Slack, generic Webhook and Schedule source settings, the new trigger flow and delete trigger, Test with sample results, secret rotation confirmation, the trigger list empty state, the queue view and cancelling a queued run, recovery options behind the Failed badge, the web workflow editor, the web command review sheet for manual launches, the web approvals surface (approval routing in HarflowMCP#42), empty and loading states, paging beyond the list, search, redelivering or replaying a delivery, and the waiting-for-approval presentation (HarflowWeb#1, HarflowWeb#2). The design's Incoming badge counts every Rejected row, while HarflowWeb#2 counts only Rejected, Couldn't start and Approval expired deliveries that arrived since Incoming was last opened. Browser checks for the sidebar and workflow editor proposals covered keyboard and focus behavior of the header control, star toggles, context menu, and confirmation dialog, the minimum-width header, deterministic reset on re-entering a route, and appearance changes preserving state; for the editor they also covered rename validation and focus trapping, pointer and keyboard reorder with cancellation, and readiness staleness; native VoiceOver behavior is unverified. The Harflow web states were checked in Light and Dark at 1000, 1200, and 1440 points in headless Chrome over a local HTTP server and from file://: keyboard use of the Incoming filters, row selection, the payload and run-input disclosures, the editor draft with Discard and condition add and remove with focus kept, Reveal, the mock Run toasts, and the navigation grouping, search, and eyebrow. The setup and teardown run states were checked in the same way for the three widths with the Command disclosure, Run teardown, and Needs attention. The setup and teardown states were checked in Light and Dark in headless Chrome over a local HTTP server and from file://: keyboard use of the setup checkbox, the Timeout spinbutton (arrow, Page, Home, and End keys and the stepper buttons within bounds), the Run when select, the Variables disclosure, and the review checkbox, the Repository edit clearing review, Discard after edits, deleting another node keeping the fields, appearance change keeping the review checkbox, and the 1000-point width with the Run sheet scrolling inside and its footer reachable. The Council configuration and run states were checked in Light and Dark in headless Chrome over a local HTTP server and from file://: accordion keyboard use with Enter and Space, focus after Add member and Remove, in-place name validation that keeps the caret, facilitator reassignment, Discard after Save, deterministic reset on re-entry, and the 1000-point width with long names and six members; the run states were checked for status badge, toolbar, spinners, roster, and feed labels. Standalone cards now precede the add control in every editor state, matching `WorkflowStandaloneBar.swift`.

## Approved start screen

The start screen replaces the empty detail pane ("Select a task") of the main window when no task or workflow is selected. Layout: a 480-point column centred in the detail pane (side padding 24, bottom padding 52, 32 points between groups). The header holds the decorative Harflow emblem (40 × 40, the title-bar template image), the greeting, and the status line. Actions are a primary New session button with a "⌘N" caption, and a tinted New workflow button shown only when at least one workflow exists. "Run a workflow" heads one grouped card of up to three workflow rows; the whole row is the Run target, labelled "Run <name>", with a 28-point tile, name, run count ("12 runs", "1 run", "Never run"), and a Run capsule. More than three workflows adds a last row "Show all N workflows". With no workflows the card reads "No workflows yet" with a description and a tinted Create workflow button, and the "Run a workflow" heading is omitted.

Greeting by local hour: 05:00–06:59 "Early start", 07:00–11:59 "Good morning", 12:00–17:59 "Good afternoon", 18:00–22:59 "Good evening", 23:00–04:59 "Working late". It never uses a name. The native greeting re-evaluates when the clock crosses a boundary while the screen is visible; the catalog cannot, so each specimen is rendered at a fixed hour (an approximation) and never reads the real clock.

Status line: a running sentence and a finished sentence joined by a space. Running: "Nothing running.", "2 tasks running.", "1 workflow running.", or "1 task and 2 workflows running." (a zero part is left out). Finished, first match wins: "N tasks finished today.", else "yesterday", else "in the last 7 days", else nothing; the finished sentence may name tasks and workflows ("4 tasks and 1 workflow finished today."). Counts agree with nouns and use digits. Decided rules: tasks started by a workflow run are not counted as tasks in the running sentence (the run counts once, as a workflow); finished workflow runs join the finished sentence. "Finished" means a task that ended Done, Failed, Timed out, or Cancelled; Running, Settling, Pending, and Needs attention are not finished. "Today" and "yesterday" are local calendar days. When counts are unavailable (the task list failed, or the store is unreadable or incompatible) the status line is omitted and the rest of the screen stays usable; while counts load, a skeleton bar about 260 × 12 points with the skeleton fill pulses, without a sweep, and stays still under Reduce Motion. Run counts that are unavailable (loading, list error) list the workflows alphabetically without counts.

Workflow order: most runs first; ties and never-run workflows sort alphabetically, localized and case-insensitive. At most three rows show.

Status line derivation from the fixtures (the populated sidebar): running are "Review session persistence" (a task) and the "Review bot" parallel run, which counts once as a workflow, so "1 task and 1 workflow running." Result: "1 task and 1 workflow running. 2 tasks finished today." The member tasks of the parallel run are not counted as tasks, including its finished member, which the sidebar shows only as "1 of 2 finished". `tasks/start-no-workflows` hides the parallel run row because no workflow is saved, so its line is "1 task running. 2 tasks finished today."
