## Task store recovery

Settings / General shows the Task store group between Managed runtime and Behaviour, as `GeneralSettingsView.swift` and `StoreRecoveryPanel.swift` do at HarflowMac `5128aeb`. The group is disabled until the managed runtime is ready. Recovery routes map to the native `StoreRecoveryPresentation.swift` states: `general` is idle ("Inspect task store"), `recovery-incompatible` is incompatible, `recovery-inspecting` is the inspected step (inspect action kept, "Review backup and reset"), `recovery-confirmation` is confirming ("Back up and reset this store?", "Confirm backup and reset"), `recovery-running` is recovering, `recovery-success` is completed, and `recovery-pre-backup-failure` is failed ("Recovery could not finish"; the engine message is a neutral fixture, and the page makes no claim about the store that the native presentation does not state). The transient native inspecting presentation has no separate route. Fixture values (state root, reason `unmarked_nonempty`, phase `proposed`, operation and backup path) follow the MonitorCore ContractsV1 fixtures under example paths. The Sessions & sidebar `store-incompatible` banner remains an exploratory proposal (#12).

`recovery-busy`, `recovery-stale`, `recovery-partial`, and `recovery-unsupported` have no native counterpart and stay exploratory (#12) in their own panel. Their fixed example paths contain no user data. These states do not imply backend behavior or pixel fidelity; native dialog sizing and Finder interaction remain unverified.

## Approved first-install setup layout

The `Sessions & sidebar` setup routes propose a left-sidebar setup cell for first install and app-paired runtime updates. Install and update actions lead to deterministic progress specimens; retries lead to the matching progress state. The busy specimens expose no duplicate action, and the catalog state selector reaches outcomes. While setup is unavailable, the sidebar hides session, workflow, search, and task controls and the main pane stays empty of task fixtures and composers. The ready specimen removes the setup card, keeps start/create controls, and shows no seeded tasks or workflows. The example update is from installed runtime `0.0.1` to the `0.0.2` required by this app; it does not imply a latest-version check or optional harness installation.

The first-install layout was explicitly approved on 2026-10-24 after browser review of `tasks/setup-required/system`. Approved reference: HarflowDesign commit `9e6a9a31bd708c2b8a1a49436923007c7a4fc659`, `scripts/sidebar-setup.js` and `styles/sidebar-setup.css`. This approval covers the compact setup card, footer, and unavailable main-pane composition; it does not approve unrelated catalog or recovery specimens. Other setup states reuse this layout with their documented state-specific content.

HarflowMac commit `1c37e4c` implements explicit installation and updates; the earlier automatic-preparation description is superseded. HarflowMac `5128aeb` implements this layout natively ("Match the approved first-run sidebar and setup welcome layout"); the approval above is unchanged. Source-derived additions after that approval: the main-window titlebar emblem beside Harflow and the connection indicator (`MainWindowEmblem.swift`, template image tinted with the label colour), and the setup card scrolling inside a 16-point inset above a fixed footer (`SidebarView.swift`). The welcome pane (20-point title, 390-point text, 470-point container) and 9/10-point setup type were already recorded. Native reference captures under `assets/references/screens/` were taken at `7fbed912` and predate the emblem. Native layout parity is under validation. The family source link retains the older baseline shell provenance. Browser controls, materials, and text rasterization remain approximations.

Deferred staleness: `tasks/install-retry` and `menu-bar/install-banner` still carry earlier wording and are not reworked in this pass.

## Not applicable and approximation boundaries

- Raw events have no source-backed search, loading, or error presentation in this sheet; only supplied events, empty events, and unknown-event treatment are represented.
- Caller-owned requests have no Harflow approval buttons. Settled or expired approvals have no active response controls.
- MCP global approvals are free-text entries, not a per-tool checkbox permission picker.
- Turn limits apply to Claude and Vibe. Antigravity does not expose xhigh effort. Native harness catalogs may vary; this fixture catalog is fixed.
- Missing/deferred task records do not imply live composer or takeover availability. Terminal workflow states do not permit Pause/Cancel.
- Library, modal, settings, and menu-bar dimensions are independent native surfaces; they are intentionally shown within a catalog stage instead of stretched to the main window.
- Canvas connectors and ports are visual baseline specimens. Drag changes mock positions; connection creation, multi-selection, split-resize, native context menus, and complete graph editing semantics are not implemented.
- Some isolated states retain surrounding fixture context for comparison. They demonstrate a specific source-derived presentation rather than a complete runtime transition simulation.
- Native fixture captures are included under `assets/references/screens/` in both appearances: sidebar, task-detail, parallel, workflow-editor, workflow-run, new-session, settings-general, settings-harnesses, and menu-bar-popover. They render actual pinned SwiftUI views at 2× scale with isolated mock data. A capture-only test passed through the source package test runner. The composed main-window capture was unsuitable as a complete reference and is excluded.
- Transparent native material regions in isolated settings/menu/sidebar captures are not palette evidence. Browser materials and host window chrome remain approximations. The foundation captures are 2000 × 1560 and accompany a 220-test validation result. Reference images are inspectable evidence, not the editable UI.

This is a local design capability, not current native or wire-contract support; request payloads cannot enable it.

Approval cards show the requested action in readable form rather than raw JSON or routine request metadata.
