## Interaction and proposed persistence

Type a draft to enable Start only with valid options and a qualified selection. Repository, harness and model changes invalidate qualification immediately; only a matching request revision can resolve it. Canonical rounded pills open anchored repository/recent-folder, combined harness/model and access menus; labeled native select controls inside approximate directory and platform popovers. Unavailable selections demonstrate explicit refusal to qualify. The catalog's Qualification ready/unavailable buttons represent cached outcomes, never provider qualification. Use the bottom-left + button (More task options) to review effort, turn limit, approval authority and permission enforcement in an anchored popover above the composer bar. Repository, harness/model and access pills remain visible. The `advanced` route opens the popover; `advanced-closed` shows retained customized options behind the closed button. A small indicator marks nondefault options against this fixture’s initial defaults (default effort, turn limit 12, harness-managed approvals), without redefining engine defaults. Enter/Space activate the native button; Escape closes and returns focus to +; outside pointer clicks close while preserving focus on the clicked control. Keyboard activation moves focus to the first option; the popover is nonmodal and does not trap focus. Its height is bounded by available space above the button and scrolls at the minimum frame. The popover reuses the existing 6px slim, rounded, secondary-color scrollbar treatment from `styles/task-activity.css`; browser scrollbars remain a native fidelity approximation. The + button retains its stable accessible name and describes whether options are customized via aria-describedby. Toggle and same-route appearance changes preserve draft/options. Field edits update validation in place without replacing focused inputs; errors remain in the composer status area when the popover closes. Supported fixture enforcement means the requested policy is reported supported, not an OS sandbox guarantee. Unknown or unsupported required enforcement blocks Start. Fixture controls switch those explicit capability outcomes. Harness-specific model menus offer Claude Opus/Sonnet, Codex gpt-6-astra, and Default; Vibe offers Default only. A prior unsupported model remains visible and blocks Start until explicitly changed, even after qualification. Turn edits immediately validate and invalidate qualification without waiting for blur; the entered value survives appearance changes. Invalid/unsupported choices never silently fall back. Every request option change invalidates qualification; refusal/unknown outcome evidence remains retained until an explicit review/reset action.

Start is single flight. Catalog completion controls explicitly resolve created/refused/unknown outcomes; there are no arbitrary timers. Definitive refusal retains the draft and offers Review settings. Unknown outcome retains and locks the submitted draft and settings, blocks retry, and offers Review Recent work without asserting whether a task exists. That action navigates to a known history fixture; it does not invent an API confirmation. Created is terminal in the fixture and blocks duplicate starts.

Proposed per-repository remembered choices: harness, model, access, effort, turn limit and approvals are remembered **after a valid Start** in this mounted mock, and restored on repository selection. Unsupported restored selections remain requested and block Start. Remembered choices are in-memory only, not localStorage, native preferences or task authority. Reset fixture and route changes clear all draft, selection, remembered choices and pending outcomes. Appearance changes on the same route preserve those values. Collapsing/expanding the sidebar and changing the frame preserve the draft. Owner review must decide whether and when the native product persists these choices.

History loading/empty, older-page failure and reconnect states preserve already-loaded rows where present. The selected identity remains stable even when absent from the retained page. `history-retained` retains the approved completed main identity `retry-budget` while the visible retained page contains only `events-reader`. Row identities retain their original title mapping. Older/loading-error/reconnecting states keep that same selected main; the New task navigation item is inactive. Retry older work navigates explicitly to its fixture route; it does not invent successor-discovery or transcript behavior. No search, filters or old task-level tabs are restored.

Runtime fixtures show checking, explicit install/update, progress, retained failure, retry and qualified-but-first-list-pending. Catalog Runtime ready/failure and Listing ready/failed buttons independently resolve those fixture axes. Listing failure leaves runtime qualified and offers Retry loading work, never installation. Install and Update only change the local fixture to progress. Engine versions installed 0.0.7 / required 0.0.8 are **proposed example values**, not a product pin decision. Runtime onboarding is distinct from harness qualification, MCP registration and M11 settings.
